## Архитектура

Плагин не реализует ни OAuth, ни HTTP-клиентов к моделям. Всё общение с GPT идёт через локальный `codex` CLI, всё общение с Claude из обратного направления — через `claude -p`. Это осознанное решение: токены остаются в тех хранилищах, куда их положили официальные инструменты, а плагин не становится ещё одним местом, где может утечь чужой секрет.

Три канала связи:

| Канал | Механизм | Где объявлен |
|---|---|---|
| Claude → GPT | MCP-сервер `codex` | `.mcp.json` |
| Claude → изображения | MCP-сервер `image` | `.mcp.json` |
| GPT → Claude | MCP-сервер `claude-bridge` | `~/.codex/config.toml` |

Внешних зависимостей нет. Оба MCP-сервера и MCP-клиент реализуют JSON-RPC поверх stdio средствами стандартной библиотеки Node.

### Три разных имени

Их легко перепутать, а последствия разные:

| Что | Значение | На что влияет |
|---|---|---|
| Репозиторий | `tandem` | `/plugin marketplace add VlDubr/tandem` |
| Маркетплейс (`marketplace.json` → `name`) | `tandem` | правая часть в `tandem@tandem` |
| Плагин (`plugin.json` → `name`) | `tandem` | **префикс слэш-команд и субагентов**: `/tandem:review`, `@tandem:gpt-advisor` |

Префикс никогда не опускается: даже если имя команды совпадает с именем плагина, вызов всё равно будет `/plugin:command`. Поэтому имя плагина держим коротким — оно попадает в каждую команду. Переименование `plugin.json` → `name` меняет все команды разом и ломает мышечную память пользователей, так что делать это стоит только с бампом мажорной версии.

## Внутреннее устройство

### Язык наружных текстов

Плагин писался на русском целиком, включая промпты. Промпт на русском заставляет и Codex, и Claude отвечать по-русски, поэтому для нерусскоязычного пользователя это был не «плагин с русской документацией», а плагин, меняющий язык его вывода. Английский стал языком по умолчанию, русский включается настройкой `language` (`TANDEM_LANG=ru`).

Всё, что видит пользователь или вызываемая модель, лежит в файлах `i18n*.mjs`: `i18n.mjs` (промпты и тексты ядра), `i18n-runtime.mjs` (сообщения времени выполнения), `i18n-image.mjs`, `i18n-claude.mjs`. `lang()` игнорирует значение вне набора, а не падает: сообщать об ошибке некуда. Комментарии в коде остаются русскими — их видит автор, а не пользователь.

Команды и агенты только английские: их фронтматтер индексирует Claude Code при загрузке, до того как известна хоть одна настройка.

### Определение флагов `codex exec`

Набор флагов менялся между версиями Codex: `--ask-for-approval` в ряде сборок отсутствует и вызывает `unexpected argument`. Поэтому флаги не угадываются — `capabilities()` в `codex-core.mjs` один раз читает `codex exec --help`, парсит наличие каждого флага и кэширует результат рядом с данными плагина, привязав к версии бинаря.

Вся сборка командной строки собрана в `buildArgs()`. Если запуск падает на аргументах, править нужно только там.

### Здоровье установки Codex

`codex-health.mjs` появился из-за конкретного случая: на Windows песочница не запускалась, потому что хелперы в `~/.codex/.sandbox-bin` были от 0.145–0.146-alpha, а CLI — 0.144.6. Наружу сбой выходил как `user cancelled MCP tool call` — неотличимо от отмены пользователем или мёртвого MCP-сервера. Диагностика какое-то время шла не туда.

`inspect()` сверяет версию CLI с версиями, разобранными из имён хелперов, проверяет наличие `codex-windows-sandbox-setup.exe` при включённой `[windows] sandbox` и возвращает проблемы в форме *что / почему / решение*, а не просто констатацией. `explainCodexFailure()` распознаёт и сырую форму сбоя, и замаскированную, и прямо говорит, что мост тут ни при чём.

`bypass_sandbox` переводит `codex exec` на `--dangerously-bypass-approvals-and-sandbox`. Выключен по умолчанию и защищён проверкой capabilities: он полностью снимает изоляцию, поэтому это аварийная мера на время починки установки, а не вариант настройки.

### Уровни усилий

Тот же класс ошибки, что и с моделями, только я успел наступить на него дважды: набор `reasoning effort` зависит от модели, и зашитый список устаревает молча. `gpt-5.6-sol` отвергает `minimal` ошибкой API, модели прошлых поколений его принимают.

`EFFORT_LEVELS` в `models.mjs` — намеренно широкий список для схемы MCP-инструмента, а настоящую фильтрацию делает `validateEffort()` по полю `supported_reasoning_efforts` из каталога. Как и с моделями, при неполном каталоге проверка пропускается: лучше пропустить сомнительное значение, чем отклонить рабочее.

`explainCodexFailure()` в `codex-core.mjs` дополнительно переводит ответ API в готовое действие — вытаскивает из текста ошибки список поддерживаемых значений. `denoise()` вырезает служебные строки Codex (в первую очередь рассинхрон его собственного кэша моделей), чтобы они не маскировали настоящую причину.

### Прогресс вместо слепого таймаута

`codex exec --json` стримит JSONL-ленту событий, пока агент работает: `turn.started`, `item.started/updated/completed`, `turn.completed` с расходом токенов. Типы элементов покрывают рассуждения, выполнение команд, правки файлов, вызовы MCP-инструментов, веб-поиск и обновления плана.

`codex-events.mjs` разбирает ленту и превращает в читаемый вид. Две особенности формата существенны: элементы reasoning появляются только при включённых reasoning summaries, а `type: "error"` с текстом `Reconnecting... X/Y` — это не отказ, а уведомление о повторе; `isFatalError()` их различает.

Флаг добавляется только если его нашла проверка capabilities. Без него `extractOutput()` возвращает сырой текст как есть — старый Codex деградирует к прежнему поведению, а не теряет ответ.

`codex_ask` не падает по таймауту. Он ждёт `wait_seconds` (по умолчанию 90) и, если модель ещё работает, возвращает id задачи вместе с собранной лентой. Запрос при этом **не перезапускается**: работу с самого начала ведёт отдельный процесс-воркер, ожидание — лишь чтение его журнала.

Пока вызов идёт, каждое значимое событие уходит клиенту как `notifications/progress` с монотонным счётчиком и токеном из `_meta.progressToken`. Без токена уведомления не шлются — адресовать их некуда. Обратное направление тоже работает: `notifications/cancelled` прерывает обработчик через `AbortSignal`, задача останавливается, ответ на отменённый вызов не отправляется.

Наружу идут только сводки размышлений: полного chain-of-thought Codex не отдаёт. При `model_reasoning_summary="auto"` сводок может не быть вовсе, поэтому есть настройка `reasoning_summary`.

### Два backend ревью

Настройка `review_backend` выбирает, как выполняется `codex_review`:

| Backend | Транспорт | Что делает Codex |
|---|---|---|
| `exec` (по умолчанию) | `codex exec --json` | ревьюит diff, который собрали мы и положили в промпт |
| `app-server` | `codex app-server --stdio`, JSON-RPC поверх stdio | собственный reviewer `review/start` сам решает, что читать |

`app-server.mjs` — минимальный JSON-RPC-клиент: `initialize` → `initialized` → `thread/start` → `review/start`, а уведомления приводятся к общей форме событий через `fromAppServerNotification()`, поэтому лента, журнал и `codex_progress` не различают backend. Отмена уходит как `turn/interrupt`. Протокол проверен на живом бинаре: поле `jsonrpc` в его кадрах необязательно, а счётчики токенов приходят отдельно в `thread/tokenUsage/updated` — клиент запоминает последний `tokenUsage.total` и присоединяет его к `turn.completed`, иначе на нативном пути расход токенов пропадал бы.

Откат на `exec` безопасен только **до того, как запрос ушёл в Codex**. Граница — `dispatched`, момент записи кадра в stdin, а не `accepted`, момент получения ответа: начавшееся ревью уже тратит квоту, и откат выполнил бы его дважды. Единственное исключение — явная JSON-RPC-ошибка (`error.rpc`): отказ доказывает, что ревью не началось, значит `exec` допустим.

Diff собирается и для `app-server`, но лишь как материал для этого отката. Если собрать его не удалось, нативное ревью всё равно стартует: в spec задачи пишется `allowFallback: false`, и воркер пробрасывает ошибку вместо молчаливой смены backend.

### Сбор изменений

`collectDiff()` — это ровно то, что видит ревью на `exec`, поэтому дыры в нём становятся дырами ревью. Собираются diff относительно merge-base, изменения в индексе и в рабочем дереве, новые неотслеживаемые файлы, затем свежий лог.

Пределы намеренные, и каждый объявляется в выводе, а не применяется молча: `DIFF_MAX_BYTES` 256 КБ, `DIFF_MAX_FILES` 60, `DIFF_MAX_NAMES` 400, `LOG_MAX_COMMITS` 200, для неотслеживаемых файлов — 24 КБ на файл, 128 КБ суммарно, 25 файлов, только текстовые (`isProbablyText()`).

Существенны два отказа. Файлы, похожие на секреты (`SECRETISH`), вырезаются из дифа через `git diff … -- . ':(exclude,literal)<path>'` и отмечаются как скрытые: отдать `.env` чужой модели — не ревью. А если у ветки нет общего предка с целевой, запрос отклоняется, вместо того чтобы выдать всю историю за «изменения».

### Процессная модель

Один путь для синхронных и фоновых вызовов:

```
MCP-вызов ──► job-worker.mjs ──► codex exec | codex app-server ──► JSONL-журнал задачи
                                                                        ▲
                                    followJob() читает журнал ──────────┘ и шлёт progress
```

Раньше путей было два: `spawnSync` для синхронного вызова и строка для `/bin/sh` для фонового. Оба сломаны. `spawnSync` блокировал event loop MCP-сервера на всё время работы Codex — сервер не отвечал на `ping`, и клиент рвал соединение с `MCP error -32000: Connection closed`. `/bin/sh` не существует на Windows: фоновая задача умирала до первой строки вывода и навсегда оставалась в статусе `unknown`.

Воркер переносим (`node job-worker.mjs`), ставит событиям метку времени приёма (сам Codex её не шлёт), атомарно пишет код возврата и оставляет пометку о причине завершения: `timeout`, `cancelled`, `spawn_failed`, `prompt_failed`, `app_server_failed`. `reconcile()` превращает пометку в статус — иначе отмена и таймаут выглядели бы одинаково провалившимся запуском. Дерево процессов убивается через `taskkill /T` на Windows и через группу процессов на POSIX (`proc.mjs`), причём `SIGTERM` эскалируется до `SIGKILL` через 3 с: процесс, игнорирующий мягкий сигнал, после отмены продолжал тратить квоту и править файлы.

Порядок важен с обоих концов. Запись задачи идёт **до** `spawn`: обратный порядок оставлял процесс Codex, о котором никто не знает, — невидимый и для учёта, и для отмены, поэтому сбой записи теперь убивает потомка. По завершении пометка и код возврата публикуются внутри `out.end(callback)`, после того как журнал дописан: опубликованные раньше, они показывали читателю завершённую задачу с обрезанным журналом. Воркер слушает `close`, а не `exit` — `exit` срабатывает, пока каналы ещё дочитываются.

Журнал задачи ограничен 32 МБ: при переполнении дописывается одна строка `worker_log_truncated`, и дальше не пишется ничего — сорвавшийся Codex не забьёт диск.

### Разговор с моделью

`codex exec resume <thread_id>` продолжает прежний тред. Идентификатор берётся из события `thread.started`. Существенно: у `exec resume` нет ни `--sandbox`, ни `--cd`, ни `--ask-for-approval` — режим песочницы задаётся через `-c sandbox_mode=...`, а рабочий каталог определяется каталогом процесса. Модель и уровень reasoning надо передавать на каждом ходе: без них Codex молча возьмёт текущие значения по умолчанию, и разговор уедет на другую модель.

`chat-store.mjs` хранит тред и его параметры. Замок — каталог (`mkdir` атомарен везде): два параллельных `resume` одного треда пишут в один rollout и разрушают переписку. Пропавший тред даёт явную ошибку: молча начать новый разговор значит потерять прежнюю переписку без предупреждения.

### Менеджер фоновых задач

Конечный автомат без обратных переходов:

```
running ──► done | failed | cancelled | timeout | unknown
```

Терминальные статусы неизменяемы. Это не украшение: раньше `cancelJob()` писал `cancelled`, а сработавший позже `child.on("exit")` перезаписывал статус на `done` — отменённая задача выглядела успешно выполненной.

Источник истины о завершении — **файл с кодом возврата**, а не событие в родительском процессе. Воркер пишет его атомарно (временный файл и `rename`) после того, как журнал дописан. Это даёт три вещи, которых не было у обработчика `exit`: код возврата переживает перезапуск MCP-сервера, дескрипторы не текут (родитель запускает воркера с `stdio: ignore` и отцепляет его), и нет гонки с отменой.

Всё, что нужно воркеру, едет в `.spec`-файле — бинарь, аргументы, пути, backend, таймаут, — а не в строке команды. Ничего не подставляется в шелл, шелла нет вовсе.

Процесс, исчезнувший без записи кода возврата, получает `unknown`, а не `done`: считать успехом то, о чём ничего не известно, — худший из вариантов.

### Жива ли задача на самом деле

Одного pid недостаточно: номера переиспользуются, и после перезагрузки на него отзывается чужой процесс — задача выглядела живой, а страховочный `killTree` убил бы постороннего. Воркер обновляет файл `.alive` каждые 5 с; метка свежее 30 с означает именно наш процесс (со стартовой отсрочкой 15 с). У задач прежних версий метки нет, для них остаётся старое правило по pid и возрасту — иначе все пережившие обновление задачи разом стали бы мёртвыми.

`liveJobs()` считает **процессы, а не статусы**. Отмена помечает задачу терминальной сразу, хотя воркер ещё жив и продолжает тратить квоту; если верить статусу, предел параллельных задач обходится одним `codex_cancel`. `reconcile()` убивает оставшийся процесс только когда `alive(pid)` подтверждает, что он есть.

### Предел параллельных задач

`max_parallel_jobs` (по умолчанию 4, `0` снимает предел) общий, а не по репозиториям: квота ChatGPT, память и процессорное время — один ресурс на все проекты сразу.

Проверка и запуск должны быть одной операцией, поэтому `startJob()` работает под замком-каталогом (`mkdirSync` атомарен везде). Протухший замок снимается **переименованием**, а не `rmdir` + `mkdir`: удалить и создать заново — две операции, между которыми замок успевает взять другой процесс, и следующий `rmdir` снимает уже чужой живой замок. Переименовать существующий каталог удаётся ровно одному.

### Срок хранения задач

`sweepJobs()` вызывается из `listJobs()` не чаще раза в час и трогает **только терминальные** задачи: удаляет завершённые более 7 дней назад и всё, что вышло за 200 последних, по всем расширениям задачи (`json`, `out`, `prompt`, `spec`, `code`, `note`, `cancel`, `alive`). Без этого каталог данных рос неограниченно, а каждый `.out` — полный журнал запуска Codex.

### Идентификаторы задач

`job_id` приходит от модели, поэтому проходит жёсткую валидацию `/^job-[0-9a-f]{8}$/` плюс проверку containment после `path.resolve()`. Единственная точка, где идентификатор превращается в путь, — `jobPath()`. Без этого `../../outside-job` читал файлы за пределами каталога задач и позволял передать чужой PID в `kill`.

### Редактирование `config.toml`

Файл принадлежит пользователю, поэтому все правки — только внутри маркированного блока. Тонкости, каждая из которых была багом:

- **Замена через функцию.** `str.replace(re, block)` интерпретирует `$&`, `$1`, `$'` в строке замены: путь плагина с `$&` вставлял внутрь результата старый блок. Только `replace(re, () => block)`.
- **Экранирование маркеров.** `# >>> tandem (claude) >>>` содержит скобки — в `RegExp` идёт только через `esc()`, иначе блок не находится никогда, а повторный `--link-back` плодит дубликаты.
- **Глобальная регулярка.** Блоков могло накопиться несколько; `unlink()` удаляет все.
- **Экранирование TOML-строки.** Кавычка в пути ломала файл. `tomlString()` экранирует `\`, `"` и управляющие символы.
- **Конфликт.** Если у пользователя уже есть неуправляемая `[mcp_servers.claude-bridge]`, вторая таблица сделает TOML невалидным — операция отклоняется, файл не трогается.
- **Атомарность.** Запись во временный файл и `rename`.

### Самолечение пути моста

`${CLAUDE_PLUGIN_ROOT}` меняется при каждом обновлении плагина, а каталог старой версии удаляется примерно через 14 дней. Записанный один раз путь в `config.toml` тихо устарел бы после `/plugin update`, а затем отвалился. `ensureFresh()` в `SessionStart`-хуке сверяет записанный путь с актуальным и переписывает при расхождении.

### Ограничение инструментов в `claude_task`

`--allowedTools` **не ограничивает** набор инструментов — он лишь снимает запрос подтверждения. Ограничивает доступность `--tools`. Это была реальная ошибка: административный allowlist `["Read"]` обходился одним аргументом от Codex.

`resolveTools()` считает пересечение запрошенного набора с настроенным потолком: сузить можно, расширить нет. Пустое пересечение — не повод запустить Claude без инструментов, а причина отказа с объяснением. При `write: false` инструменты записи вырезаются принудительно и дублируются в `--disallowedTools`.

### Проброс MCP-инструментов

`tool-proxy.mjs` поднимает разрешённые серверы через `mcp-client.mjs`, читает их `tools/list` и переэкспортирует под именем `<alias>__<tool>`. Падение одного сервера не ломает остальные.

Обнаружение серверов следует precedence Claude Code: **local → project → user**, первый выигрывает. Порядок важен: раньше выбирался user-сервер, перекрывая локальную настройку разработчика.

Переменные окружения хранятся в allowlist **только как ссылки** `${VAR}` / `${VAR:-default}` — `sanitizeEnv()` отбрасывает литеральные значения, чтобы чужие токены не оказались в файле плагина. Раскрытие происходит при запуске сервера.

### Генерация изображений

Codex без явного запрета склонен вместо встроенного `image_gen` написать Python- или Node-скрипт к платному Images API. Промпт в `buildPrompt()` закрывает этот путь тремя отдельными формулировками, а `generateImage()` распознаёт срыв по выводу (`OPENAI_API_KEY`, `api.openai.com`, `images/generations`) и говорит об этом прямо.

Результат принимается только после проверок:

1. код возврата Codex — **до** поиска файлов, иначе подберём чужой артефакт;
2. `sniffImage()` — magic bytes PNG/JPEG/GIF/WebP, а не расширение и не слова Codex;
3. `resolveInside()` — `out_dir` и референсы не выходят за корень проекта, абсолютные пути запрещены;
4. `acceptableSource()` — путь из строки `SAVED:` принимается только изнутри проекта или `$CODEX_HOME/generated_images/`.

Fallback-поиск свежего файла в каталоге Codex тоже фильтрует по сигнатуре.

### Каталог моделей

`codex debug models` → парсинг с сужением среза с обеих сторон (каталог бывает окружён служебными строками) → кэш на 6 часов.

При недоступности подкоманды — деградация на `model` из `config.toml`, затем на устаревший кэш. Такой каталог помечается `complete: false`, и `knownModel()` по нему **не блокирует** незнакомые модели: иначе отклонялись бы вполне рабочие имена.

### MCP-транспорт

`mcp-lib.mjs` объявляет поддерживаемые версии явно (`2025-06-18`, `2025-03-26`) и отвечает запрошенной, только если умеет её; иначе своей. Битый JSON даёт `-32700 Parse error`, а не молчание. Наружу уходит только сообщение об ошибке — stack trace пишется в stderr, чтобы не раскрывать пути и внутреннее устройство.

Батчи JSON-RPC отклоняются осознанно: они удалены из MCP в ревизии 2025-06-18, которую сервер и объявляет.

Форма входящего сообщения проверяется до разбора полей. `null` и скаляры — синтаксически верный JSON, и деструктуризация такого сообщения выбрасывала исключение внутри асинхронного обработчика `line`, которое никто не ловит: сервер умирал целиком вместе со всеми живыми вызовами. Теперь это `-32600`. Строка больше 16 МБ отклоняется до `JSON.parse`, который иначе удвоил бы память, стоящую такой строки.

`mcp-client.mjs` реагирует на `exit`/`close` вложенного сервера немедленным отказом всех ожидающих запросов и сохраняет хвост его stderr — без этого вызов после смерти сервера висел до полного таймаута, а причина сбоя терялась.

## Тесты

```bash
node tests/regressions.mjs
```

119 тестов, по одному на каждый известный дефект. Настоящие `codex` и `claude` не нужны: тест сам создаёт заглушки во временном каталоге, поведение которых задаётся переменными окружения.

Покрыто: определение флагов, терминальные статусы задач, код возврата после перезапуска, утечка дескрипторов, path traversal в `job_id`, обход allowlist инструментов, принудительный read-only, подмена изображения произвольным файлом, containment путей, порча `config.toml` (`$&`, кавычки, дубликаты, конфликты), обработка ненулевого кода возврата, права файлов и отбрасывание секретов, деградация каталога моделей, разбор аргументов `setup`, precedence MCP, version negotiation, parse error, скаляр вместо сообщения не роняет сервер, предел длины входящей строки, утечка stack trace, реакция на смерть вложенного сервера, предел параллельных задач и его замок, метка жизни против переиспользованного pid, обрезание журнала и кириллица на границе чтения, секреты вне дифа, отказ без общего предка, нативный backend ревью и граница отката, не позволяющая потратить квоту дважды.

28 из них требуют POSIX: заглушки — shebang-скрипты, а права `0600` и кавычки в именах файлов на Windows ничего не значат. Такие тесты честно помечаются пропущенными, а не выдаются за пройденные. Тест утечки дескрипторов дополнительно требует `/proc` и вне Linux пропускается.

CI (`.github/workflows/tests.yml`) гоняет набор на `ubuntu-latest` и `windows-latest` против Node 20.11 и 22, плюс отдельная задача `validate` для `claude plugin validate . --strict`. Матрица появилась не зря: она сразу вскрыла настоящие поломки — 28 тестов, никогда не выполнявшихся на Windows, падали на Linux, потому что английский вывод по умолчанию сверялся с русскими подстроками, заглушка теряла буферизованный вывод из-за `process.exit`, а `node -e` до Node 20 разбирается как CommonJS и не принимает top-level `await`.

Тесты совместной работы находятся в `tests/collaboration.mjs` (состояние, бюджет, фазы, восстановление) и `tests/collaboration-bridges.mjs` (оба MCP-входа с переносимыми заглушками CLI). Общий регрессионный запуск выполняет их встроенным тестовым раннером Node, поэтому существующая матрица CI проверяет их без зависимостей. Отдельный запуск: `node --test tests/collaboration.mjs tests/collaboration-bridges.mjs`.

### Протокол совместной работы

`CollaborationSession` в `scripts/collaboration.mjs` отвечает за общий жизненный цикл; `scripts/i18n-collaboration.mjs` — за английские и русские схемы и промпты. Адаптер Codex использует существующие воркеры и публикует идентификатор задачи до ожидания; опрос никогда не запускает новую задачу. Адаптер Claude использует существующий отменяемый процесс с инструментами Read/Grep/Glob. Нативное продолжение треда и автономный цикл не добавляются.

Ключ состояния — хеш канонического рабочего каталога, backend и проверенного имени сессии. JSON сохраняется атомарно в каталоге данных плагина; существующий замок с меткой жизни сериализует изменения. Раунд резервируется до вызова модели, ошибка и отмена тоже его расходуют. Этап содержит шесть вызовов и последовательные фазы выбранного режима. Успешный синтез закрывает этап; явное продление требует сводки и подтверждения вызывающей стороны. Полный диалог остаётся локально; промпт содержит только сводку, текущий этап и явно ограниченные фрагменты ответов. Локальный путь к состоянию второй модели не передаётся.

Схема состояния — версия 2. Файлы версии 1 переводятся в памяти при чтении и сохраняются как версия 2 при следующей записи под замком; одно чтение файл не переписывает. Старая версия плагина файлы версии 2 не прочитает.

Режим `compare` хранит `commitment` ведущей модели по этапам вместе с SHA-256. Он принимается один раз — с первым ходом `solve`, до любого вызова этапа — и попадает в промпт как `host_commitment` только начиная с фазы `compare`. Сообщение `solve`, дословно содержащее ответ, отклоняется; пересказ обнаружить нельзя.

Учёт токенов: каждый завершённый раунд хранит `usage` (`tokens`, `estimated`), и итог сессии обязан равняться их сумме. Для Codex берётся `input_tokens − cached_input_tokens + output_tokens` из `turn.completed`; Claude в совместной работе запускается с `--output-format json`, учитываются `input_tokens + output_tokens` без чтения и записи кеша, которые повторяются на каждом внутреннем шаге агента. Отсутствующий расход (старый CLI, сбой, отмена) оценивается как `ceil(символы / 3)` промпта и ответа. `max_tokens` мягкий: проверяется до хода под замком.

`collaboration-codex.mjs` получает список настроенных MCP-серверов и отключает каждый по имени: `mcp_servers={}` объединился бы с унаследованной таблицей, а не очистил её. Также отключаются hooks, plugins, apps и multi-agent; обход песочницы запрещён. Окружение воркера содержит признак вложенного вызова, и оба моста запрещают рекурсию. Эти меры не фильтруют секреты и не аутентифицируют согласие человека на продолжение.

## Публикация

Репозиторий одновременно является плагином и маркетплейсом из одного плагина: `.claude-plugin/marketplace.json` лежит в корне, его единственная запись указывает `"source": "."` — на сам корень.

```bash
claude plugin validate . --strict
```

Проверяет манифест, фронтматтер команд и агентов, `hooks.json`. Флаг `--strict` превращает предупреждения в ошибки — полезно в CI.

### Версионирование

В `plugin.json` задано `"version"`. Пока поле установлено, пользователи получают обновления **только после его повышения**: новых коммитов недостаточно, Claude Code видит ту же строку версии и оставляет закэшированную копию.

На этапе активной разработки поле можно удалить — тогда версией станет SHA коммита и обновления пойдут с каждым пушем.

Единственный источник версии — `plugin.json`: его читает `version.mjs`, а оба MCP-сервера передают результат в `serve({ version })`. При бампе больше править нечего.

### Несколько плагинов в репозитории

Если появятся другие плагины, перенесите текущий в `plugins/tandem/` и поменяйте `source` на `"./plugins/tandem"`. Пути в записях разрешаются относительно каталога, содержащего `.claude-plugin/`.

## Отладка

```bash
claude --plugin-dir /путь/к/tandem   # запуск без установки
claude --debug                             # загрузка плагина, инициализация MCP
/tandem:setup                               # диагностика окружения
```

MCP-сервер можно позвать напрямую:

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
  | node scripts/mcp-codex.mjs
```

Обратный мост — так же, `node bridge/mcp-claude.mjs`; он читает allowlist из `TANDEM_EXPOSED` (по умолчанию `~/.codex/tandem/exposed.json`).

Полезные переменные окружения для тестов и отладки: `CODEX_BIN`, `CLAUDE_BIN`, `CLAUDE_PLUGIN_DATA`, `TANDEM_CONFIG`, `TANDEM_EXPOSED`, `CODEX_HOME`.

Каждая настройка плагина приходит и как переменная окружения — именно так их задают тесты: `TANDEM_LANG`, `TANDEM_MODEL`, `TANDEM_EFFORT`, `TANDEM_REASONING_SUMMARY`, `TANDEM_REVIEW_BACKEND`, `TANDEM_PROGRESS`, `TANDEM_MAX_PARALLEL_JOBS`, `TANDEM_JOB_TIMEOUT_MIN`, `TANDEM_IMAGE_DIR`, `TANDEM_IMAGE_TIMEOUT_MIN`, `TANDEM_BYPASS_SANDBOX`.

## Непроверенные допущения

Честный список того, что не проверялось на живых бинарях:

1. **Ограничения `aspect_ratio` / `image_resolution`** (`auto` только с `1K`, `1:1` без `4K`) взяты из документации стороннего API и для встроенного `image_gen` не подтверждены. Могут отклонять допустимые параметры — снимаются двумя строками в `validate()` в `image-core.mjs`.
2. **Формат вывода `codex debug models`** разбирается терпимо (`parseCatalog()`), но на реальном выводе не проверялся.
3. **Точный набор флагов `codex exec`** определяется по `--help`; парсинг help-текста регулярками сам по себе допущение.
4. **Поведение `claude -p --tools`** проверено по документации, не на реальном бинаре.

Протокол `codex app-server` из этого списка выбыл: имена методов, необязательность поля `jsonrpc`, форма item и счётчики `thread/tokenUsage/updated` проверены на живом бинаре.

Первый прогон на настоящем окружении должен идти по возрастанию риска: `/tandem:setup` → `/tandem:models` → `/tandem:review` → `/tandem:delegate` → `/tandem:image`.

## Вклад

Правки принимаются с тестом на исправляемое поведение. Изменения, затрагивающие безопасность (allowlist инструментов, containment путей, права файлов, редактирование `config.toml`), должны сопровождаться тестом, который падает без правки.
